Chapter 2 — Routes, Navigation & App Lifecycle

This covers how Flutter moves between screens (routes, Navigator, passing data) and the 4 states an app goes through while it runs (Resumed, Paused, Inactive, Detached). Theory only — from your lecture slides.

MODULE 2

What is a route? EXAM

Lecture 2, slide 4 — Chapter_2_App_Lifecycle.pdf

A screen or page in your app is called a route. This is just a name — a route is nothing more than one "page" the user sees.

Q1. What does "route" mean in Flutter?

Answer

In Flutter, screens and pages are called routes. A route is just a widget — that's it. No special class needed, any widget can be a screen.

Q2. What is a "route" called in Android and iOS?

Answer

Same idea, different name per platform. See table below.
PlatformWhat a "screen" is called
FlutterRoute (just a widget)
AndroidActivity
iOSViewController
Simple way to remember

Route = Activity = ViewController. Same concept ("one screen"), 3 different names depending on which platform you talk about.

Extra note from slides

When your app needs advanced navigation (e.g. complex deep linking), the slides mention using a routing package such as go_router instead of plain Navigator.

Where to find it

Chapter_2_App_Lifecycle.pdf — slide 4 to 5 (Route and Navigator intro).

More practice

True or False: a route in Flutter must be a special "Route" class.
False. A route is just a normal widget — any widget can act as a screen.
What package do the slides suggest for advanced/complex navigation?
go_router — used for complex deep linking and advanced routing needs.
Navigation

The Navigator stack EXAM

Lecture 2, slide 6–9

The Navigator widget is like a stack of plates. Think of it literally — you can only add a plate on top, and only remove the top plate. You can never grab a plate from the middle.

Q1. How does the Navigator stack work?

Answer

  • Navigator shows screens as a stack — last screen added = the one on top = the one the user sees.
  • It also plays the correct transition animation for the platform (slide-in on iOS, fade/slide on Android).
  • Good for small apps without complex deep linking.
Screen 1 (Main)
Start → Screen 1 only
Screen 1 (Main)
Screen 2
push() → Screen 2 on top
Screen 1 (Main)
Screen 2
Screen 3
push() → Screen 3 on top
Screen 1 (Main)
Screen 2
pop() → Screen 3 destroyed
Screen 1 (Main)
pop() → Screen 2 destroyed

Q2. What happens when you call Navigator.push()?

Answer

See flow below.
1
User taps a button on the current screen (e.g. an item in a list).
2
App calls Navigator.push(context, ...) using the current route's BuildContext.
3
A new screen (built with MaterialPageRoute) gets placed on top of the stack.
4
Flutter plays a transition animation matching the target platform (e.g. slide from right).
5
The new screen is now visible; the old screen is still in the stack underneath, just not visible.

Q3. What happens when you call Navigator.pop()?

Answer

See flow below.
1
User taps a "back" button (or the system back gesture/button).
2
App calls Navigator.pop(context).
3
The top screen is removed (destroyed) from the stack.
4
The screen underneath it becomes visible again — this is the previous screen the user was on.
Push vs Pop, in one line

push() = add a new screen on top (go forward). pop() = remove the top screen (go back).

Where to find it

Chapter_2_App_Lifecycle.pdf — slide 6 (Navigator intro), slide 7 (stack diagram), slide 8 (push), slide 9 (pop).

More practice

If Screen 1 → Screen 2 → Screen 3 are all pushed, and the user presses back once, which screen do they see?
Screen 2. Only the top of the stack (Screen 3) is removed; Screen 2 was directly underneath it.
Is Navigator (plain push/pop) good for apps with complex deep linking?
No — the slides say Navigator suits small apps without complex deep linking. For advanced cases, use go_router.
Passing Data

Sending data to a new screen

Lecture 2, slide 10–14

Often you don't just want to go to a new screen — you want to bring data with you. Example from the slides: tapping a TODO item in a list should open a detail screen showing that exact TODO's info.

Q1. How does data travel from one screen to the next?

Answer

Data is passed through the new screen's constructor — the same way you'd pass any value into a class.
1
Main screen has a list of items (e.g. todos[]), each one is a data object (e.g. a Todo with title + description).
2
User taps one item, e.g. todos[index].
3
App calls Navigator.push() and builds the detail screen, passing that one Todo object into its constructor.
4
The Detail screen widget requires a Todo in its constructor and stores it as a field.
5
Detail screen displays the data (title, description) straight from that object — no extra fetching needed.

Screen A (List)

Holds the full list of data objects. Knows which item was tapped.

The Data Object

A plain class (e.g. Todo) holding related fields — title, description, etc.

Screen B (Detail)

Constructor requires the data object as a parameter. Displays its fields directly.

Key idea

You are not sending data through some special "message system" — you're just passing a normal object into a widget's constructor, exactly like passing an argument into any Dart class.

Where to find it

Chapter_2_App_Lifecycle.pdf — slide 10 (why), slide 11 (diagram: TODO list → Detail), slide 12–14 (Todo class + DetailScreen + push with data).

More practice

In the TODO example, what mechanism carries the Todo data from list screen to detail screen?
The DetailScreen's own constructor — the Todo object is passed in as a required constructor parameter when the screen is built.
Does the Detail screen need to fetch its own data separately?
No — it already receives the exact data object it needs through its constructor field.
Passing Data Back

Returning data from a screen

Lecture 2, slide 15–16

Sometimes the flow is reversed: Screen B needs to send something back to Screen A. Example: user picks an option on Screen B, and Screen A needs to know what was picked.

Q1. How does data flow back to the previous screen?

Answer

Data goes back through Navigator.pop(context, data) plus a .then() callback on the original push.
1
Screen A calls Navigator.push() to open Screen B, and attaches a .then((value) { ... }) callback right after the push.
2
User interacts with Screen B (e.g. selects an item, fills a form).
3
Screen B calls Navigator.pop(context, 'Returned Data') — the second argument is the data being sent back.
4
Screen B is removed from the stack (normal pop behaviour), and control returns to Screen A.
5
The .then() callback on Screen A fires automatically, receiving that returned value — Screen A can now setState() to use it.
Push vs Pop-with-data

Sending data forward = constructor parameter (see previous section). Sending data backward = second argument of Navigator.pop(context, data), read via .then().

Where to find it

Chapter_2_App_Lifecycle.pdf — slide 15 (concept + pop with data), slide 16 (push + .then() callback).

More practice

Which Flutter method lets Screen A "catch" the value Screen B sends back?
.then() — chained onto the original Navigator.push() call.
What is the second argument of Navigator.pop(context, value) used for?
It is the data being returned to the previous screen — without it, pop() just goes back with no data.
State Management

Shared state across screens (Provider)

Lecture 2, slide 17–20

Passing data through constructors and pop() works fine for 2 screens. But what if many screens across the app need the same data, and any of them might update it? That's where Provider comes in.

Q1. Why use Provider instead of just passing data screen-to-screen?

Answer

For more complex situations, the slides recommend a state management solution like Provider. It lets you share data across multiple screens and update it from any part of the app — not just the 2 screens directly involved in one push/pop.
1
ChangeNotifier holds the data — a class (e.g. DataProvider) stores the shared value and calls notifyListeners() whenever it changes.
2
Provider shares it — the DataProvider instance is made available to the widget tree, so any screen underneath can access it.
3
Consumer screens read and rebuild — any screen wrapped in a Consumer<DataProvider> automatically rebuilds itself whenever the data changes.

ChangeNotifier

Holds the actual data. Has a method to update the value + call notifyListeners().

Provider

Makes that ChangeNotifier instance reachable from anywhere lower in the widget tree.

Consumer

Wraps a widget so it listens for changes and rebuilds automatically when data updates.

Compare to constructor passing

Constructor passing = one-time data hand-off between exactly 2 screens. Provider = a shared "data box" any screen in the whole app tree can read from and write to.

Where to find it

Chapter_2_App_Lifecycle.pdf — slide 17 (why Provider), slide 18 (ChangeNotifier), slide 19 (Consumer on First Screen), slide 20 (updating data on Second Screen).

More practice

What method must a ChangeNotifier call after updating its data, so listening widgets know to rebuild?
notifyListeners() — this tells every Consumer watching this provider to rebuild with the new value.
If 5 different screens all need the same login info, is constructor-passing or Provider the better fit?
Provider — because the data needs to be shared and updated from many parts of the app, not just handed off between 2 screens.

Deep linking

Lecture 2, slide 21–23

Normally, opening an app takes you to the home screen. Deep linking skips that — a link opens the app straight to one specific screen or piece of content.

Q1. What is deep linking?

Answer

  • Deep linking = linking directly to specific content inside an app.
  • Lets a user open the app straight to a particular screen or feature — not just the home screen.
  • Flutter supports deep linking on iOS, Android, and web.
  • Opening the URL displays that exact screen in the app.

Q2. What does a deep link URL look like?

Answer

A normal-looking URL, split into 3 parts.
PartExampleMeaning
Schemehttps://The protocol used to open the link
Domaindashcast.netWhich app/website owns this link
Path/library/album/1Exactly which screen/content to open (here: album #1)
One link, two destinations

The same link (e.g. https://dashcast.net/library/album/1) can open the web page in a browser, or the app directly to that album screen — same URL works for both.

Q3. How does deep linking differ between Android and iOS?

Answer

Each platform has its own name for the same idea.
PlatformNameNotes
AndroidApp linkDeep link using http/https, exclusive to Android devices
iOSUniversal linkApple's deep link implementation for iOS

Chapter_2_App_Lifecycle.pdf — slide 21 (concept), slide 22 (URL breakdown diagram), slide 23 (app link vs universal link).

More practice

What is the Android-specific name for a deep link using http/https?
App link.
What is the iOS-specific name for the same concept?
Universal link.
In the URL https://dashcast.net/library/album/1, which part is the "path"?
/library/album/1 — it tells the app exactly which screen/content to open.
App Lifecycle

The Flutter app lifecycle EXAM: Q1b

Lecture 2, slide 24–34

While your app runs, it moves through different states — like being on-screen, in the background, or fully closed. Knowing these states lets you manage resources properly (battery, memory, saved data).

Exact exam question (Question 1b)

Resumed, Paused, Inactive, Detached.

Q2. What does each state mean, and what should you do in it?

Answer

See table below — this is the core exam table.
StateVisible?What it meansSuitable task example
1. ResumedYesIdeal state — app is on screen, actively responding to the userFetch/display data, process taps & swipes, play audio/video, start animations
2. InactivePartlyBrief transition between Resumed and Paused — app may lose focus but is still in memoryBriefly pause a network request; prepare for a possible state change
3. PausedNoApp is in the background with limited functionalityPause animations/location updates, save unsaved user data, release unneeded resources
4. DetachedNoApp is not attached to any view and isn't actively runningClean up resources (close databases), persist critical data before closing

1. Resumed

App is visible, active, responding to user.

  • Fetch/display data
  • Process interactions
  • Play audio/video
  • Start animations

2. Inactive

Transitional — losing focus, still in memory.

  • Pause a network request briefly
  • Prepare for next state change

3. Paused

In background, limited function.

  • Pause resource-heavy tasks
  • Save unsaved data
  • Release unneeded resources

4. Detached

Not attached to any view, not running.

  • Clean up (close DB, free memory)
  • Persist critical data
  • No UI actions here
Common mix-up

Inactive ≠ Paused. Inactive is a short, in-between moment (app still fully in memory, might resume any second). Paused is a longer background state where the app expects to possibly be suspended soon. Don't do heavy work in either — but especially avoid it in Paused.

Q3. What real actions on the phone trigger each transition?

Answer

The slides describe the states conceptually; typical real-world triggers are shown below (general Flutter knowledge, matched to the slide definitions).
User actionLikely transition
App opens, user is using it normally→ Resumed
Incoming phone call, or system dialog (e.g. permission popup) appears→ Inactive
User presses Home button, or switches to another appResumed → Inactive → Paused
User swipes the app away from recent apps / app is closedPaused → Detached
App reopened from backgroundPaused → Inactive → Resumed

Q4. How do you monitor these lifecycle changes in code?

Answer

  • The AppLifecycleState enum holds the current state value.
  • The AppLifecycleListener class lets you register callbacks for each transition — e.g. onResume, onPause, onInactive, onDetach, onShow, onHide, onRestart.
  • There's also a general onStateChange callback that fires on every state change (the specific callbacks above only fire for their exact transition).
  • Handling these properly lets you optimize resource usage — e.g. pause timers or save data when going to background, and respond correctly when resuming.
Why this matters (exam-relevant reasoning)

Managing lifecycle correctly = better battery life, no data loss, and a smoother experience when switching apps. This connects to Chapter 1's "mobile devices have limited battery/memory" problem — lifecycle handling is part of the solution.

One-paragraph recap

  • A route = a screen = a widget in Flutter (Activity in Android, ViewController in iOS).
  • Navigator manages screens like a stack: push() adds, pop() removes the top.
  • Data going forward = constructor parameter. Data going back = Navigator.pop(context, data) caught by .then().
  • Provider (ChangeNotifier + Consumer) is for sharing/updating data across many screens, not just 2.
  • Deep linking opens the app straight to specific content via a URL; Android calls it "app link", iOS calls it "universal link".
  • 4 lifecycle states: Resumed (active/visible), Inactive (brief transition), Paused (background), Detached (not running).
  • AppLifecycleState (enum) + AppLifecycleListener (class with callbacks) let you monitor and react to state changes.

Common mistakes to avoid

  • Mixing up push() and pop() direction — push = forward/new screen, pop = backward/remove screen.
  • Confusing Inactive with Paused — Inactive is brief and app is still fully in memory; Paused is longer, background, and app might get suspended.
  • Forgetting the exact 4 state names and order: Resumed, Paused, Inactive, Detached (as listed in the slides) — but conceptually the transition order in real use is Resumed ⇄ Inactive ⇄ Paused ⇄ Detached.
  • Thinking data must go back via constructor too — returning data uses pop(context, data) + .then(), not a constructor.
  • Thinking Provider replaces Navigator — they solve different problems (state sharing vs screen navigation), used together.
