Chapter 2 — Routes, Navigation & App Lifecycle

How Flutter moves between screens, passes data, and manages app lifecycle states. Built from lecture slides, designed for quick revision.

MODULE 2

What are routes?

In Flutter, every screen (page) you see is called a route. A route is just a widget. When you move from one screen to another, you are navigating between routes.

Routes across platforms

PlatformWhat a "screen" is calledExample
FlutterRoute (widget)MaterialPageRoute
AndroidActivityMainActivity
iOSViewControllerUIViewController
Key idea

In Flutter, you do not create "Activities" or "ViewControllers". You create a Widget and the Navigator shows it as a new screen.

// A route is just a widget in a MaterialPageRoute Navigator.push( context, MaterialPageRoute(builder: (context) => SecondScreen()), );

Practice questions

Q1. What is a route in Flutter?
A route is a screen/page in the app. In Flutter, a route is a widget shown by the Navigator.
Q2. What is Android's equivalent of a Flutter route?
An Activity (e.g. MainActivity).
Navigation

The Navigator stack

The Navigator keeps screens in a stack (like a pile of plates). When you open a new screen, it goes on top. When you go back, the top screen is removed.

Screen 1 Home
→
Screen 2 Detail
→
Screen 3 Settings

↑ Screen 3 is on top (visible). Screen 2 is behind it. Screen 1 is at the bottom. When Screen 3 pops, Screen 2 becomes visible again.

Key Navigator methods

MethodWhat it does
Navigator.push()Adds a new screen on top of the stack
Navigator.pop()Removes the top screen (goes back)
Navigator.popUntil()Goes back to a specific screen in the stack
Navigator.pushReplacement()Replaces current screen instead of adding on top
Stack rule

You can only see the top screen. You can only go back by popping the top. You cannot jump to the middle of the stack directly (use popUntil for that).

Practice questions

Q1. What data structure does Navigator use to manage screens?
A stack (last-in, first-out). Screens are pushed on top and popped from the top.
Q2. What happens when you call Navigator.pop()?
The top screen is removed from the stack. The previous screen becomes visible again.
Navigation

Navigator.push() and Navigator.pop()

Navigator.push()

Opens a new screen. You must provide a MaterialPageRoute with the target widget.

Navigator.push( context, MaterialPageRoute( builder: (context) => DetailScreen(), ), );
  • context — the current screen's position in the widget tree
  • MaterialPageRoute — provides the slide animation (left to right on Android, bottom to top on iOS)
  • builder — a function that returns the new screen widget

Navigator.pop()

Closes the current screen and goes back to the previous one.

Navigator.pop(context);
Common mistake

Forgetting to pass context to pop(). Without it, Flutter does not know which Navigator to use.

Practice questions

Q1. Write the code to push a new screen called ProfileScreen.
Navigator.push(context, MaterialPageRoute(builder: (context) => ProfileScreen()));
Q2. What animation does MaterialPageRoute provide on Android?
A slide from left to right. On iOS, it slides from bottom to top.
Data Passing

Send data between screens

You can pass data from one screen to another by sending it through the constructor of the target widget.

Main Screen (sender)

Creates the target widget and passes data as a constructor argument.

Navigator.push( context, MaterialPageRoute( builder: (context) => TodoScreen( todo: Todo('Buy milk', 'Low'), ), ), );

Detail Screen (receiver)

Receives the data in its constructor and uses it.

class TodoScreen extends StatelessWidget { final Todo todo; const TodoScreen({required this.todo}); Widget build(BuildContext context) { return Text(todo.title); } }
1
Main screen creates a Todo object with data (title, priority).
2
Main screen calls Navigator.push() and passes the Todo object to the detail screen's constructor.
3
Detail screen receives the Todo in its todo parameter.
4
Detail screen displays todo.title and todo.priority.
Exam tip

Data passing uses constructor injection — you pass the data as a parameter when creating the widget. This is the simplest and most common way to pass data in Flutter.

Practice questions

Q1. How do you pass a string userName to a ProfileScreen?
Navigator.push(context, MaterialPageRoute(builder: (context) => ProfileScreen(name: userName))); — and ProfileScreen must have a constructor that accepts name.
Q2. What is the technical name for this data passing pattern?
Constructor injection — passing data as constructor parameters.
Data Passing

Return data from a screen

Sometimes you need the second screen to send data back to the first screen (e.g. user selects an item and the first screen needs to know which one).

1
Screen A pushes Screen B using Navigator.push().
2
Screen B does some work (e.g. user picks an option).
3
Screen B calls Navigator.pop(context, 'Returned Data') — the second argument is the data to send back.
4
Screen A receives the data using .then() callback.

Code example — Screen B (sender)

ElevatedButton( onPressed: () { Navigator.pop(context, 'Yes, I confirm'); }, child: Text('Confirm'), ),

Code example — Screen A (receiver)

final result = await Navigator.push<String>( context, MaterialPageRoute(builder: (context) => ConfirmScreen()), ); if (result != null) { print('User said: $result'); }
Alternative: .then() callback

You can also use Navigator.push(...).then((value) { ... }) if you don't want to use async/await.

Practice questions

Q1. What method sends data back from Screen B to Screen A?
Navigator.pop(context, data) — the second argument is the data you want to return.
Q2. How does Screen A receive the returned data?
Using await Navigator.push<String>(context, ...) or using .then((value) { ... }).
State Management

Shared state with Provider

When multiple screens need to share the same data (e.g. a shopping cart), passing data via constructors becomes messy. Provider solves this by giving all screens access to the same data.

How Provider works

1
ChangeNotifier — a class that holds the shared data and notifies listeners when data changes.
2
ChangeNotifierProvider — wraps the app and creates the ChangeNotifier instance at the top.
3
Consumer — any screen can use a Consumer to listen to changes and rebuild its UI.

Code example

// 1. Create a ChangeNotifier class CartProvider extends ChangeNotifier { final List<Item> items = []; void add(Item item) { items.add(item); notifyListeners(); // tells all Consumers to rebuild } } // 2. Wrap the app with Provider void main() { runApp( ChangeNotifierProvider( create: (context) => CartProvider(), child: MyApp(), ), ); } // 3. Any screen can access the shared data Consumer<CartProvider>( builder: (context, cart, child) { return Text('Items: ${cart.items.length}'); }, ),
Provider vs Navigator passing

Navigator passing = one-time, point A to point B. Provider = shared, real-time, any screen can read/write the same data.

Practice questions

Q1. When should you use Provider instead of passing data via Navigator?
When multiple screens need to share and update the same data (e.g. shopping cart, user profile, theme settings).
Q2. What does notifyListeners() do?
It tells all Consumer widgets to rebuild their UI with the updated data.
Navigation

Deep linking

Deep linking lets users open a specific screen inside your app directly, instead of always starting from the home screen. For example, clicking a link opens the app directly at a product page.

Deep linking by platform

PlatformTermHow it works
AndroidApp LinksURL maps to a specific Activity/screen via intent filters in AndroidManifest.xml
iOSUniversal LinksURL maps to a specific screen via associated domains in the Apple app site association file
Fluttergo_router / auto_routeFlutter packages that handle URL parsing and map URLs to routes
Exam tip

Deep linking is like a shortcut. Instead of: Open app → Home → Menu → Product → Item, the user clicks a link and goes directly to: Open app → Item.

Practice questions

Q1. What is deep linking?
The ability to open a specific screen inside an app directly from a URL or link, skipping the home screen.
Q2. What is the Android term for deep linking?
App Links.

App lifecycle states

When a user opens, switches away from, or closes your app, the app moves through different lifecycle states. Knowing these states helps you manage resources (pause videos, save data, stop network requests).

The 4 primary states

Resumed
Visible & active
→
Inactive
Brief transition
→
Paused
In background
→
Detached
Not attached

State details

StateVisible?What happensWhat you should do
ResumedYesApp is in the foreground, user can interactPlay animations, fetch data, enable input
InactivePartiallyBrief transition (e.g. incoming call dialog, app switcher)Pause animations, reduce activity
PausedNoApp is in background, not visible to userPause videos, save user data, stop network requests
DetachedNoApp is not attached to any engine (being destroyed)Clean up resources, persist critical data
Exam question (from mock test!)

The mock test asks: "Identify the 4 primary states in Flutter app lifecycle and provide a task example for each." This is worth 8 marks. Memorize the table above.

Task examples for each state

R
Resumed — play a video, start a timer, fetch latest data from API, show animations.
I
Inactive — pause a game, stop a countdown, reduce frame rate.
P
Paused — pause music, save current progress to local storage, stop GPS tracking.
D
Detached — close database connections, save unsaved data, release camera/sensor resources.

Practice questions

Q1. List the 4 Flutter app lifecycle states.
Resumed, Inactive, Paused, Detached.
Q2. When the user switches to another app, which state does your app enter?
First Inactive (brief transition), then Paused (background).
Q3. Give one task example for the Paused state.
Pause music, save user progress, stop GPS tracking, close network connections.
Lifecycle

AppLifecycleListener

Flutter provides the AppLifecycleListener class to watch for lifecycle changes. You can run code when the app enters each state.

Code example

class _MyAppState extends State<MyApp> { late final AppLifecycleListener _listener; @override void initState() { super.initState(); _listener = AppLifecycleListener( onShow: () => print('App visible'), onResume: () => print('App resumed'), onHide: () => print('App hidden'), onInactive: () => print('App inactive'), onPause: () => print('App paused'), onDetach: () => print('App detached'), onRestart: () => print('App restarted'), ); } @override void dispose() { _listener.dispose(); super.dispose(); } }
Exam tip

You don't need to memorize every callback name. Just know that AppLifecycleListener exists and has callbacks for each lifecycle state (onResume, onPause, onDetach, etc.).

Practice questions

Q1. What class do you use to listen to lifecycle changes in Flutter?
AppLifecycleListener.
Q2. What callback runs when the app goes to the background?
onPause (and onHide for visibility changes).

One-paragraph recap

  • Every screen in Flutter is a route (a widget). The Navigator manages routes as a stack.
  • Navigator.push() opens a new screen; Navigator.pop() closes the current one.
  • Pass data to a new screen via its constructor. Return data using Navigator.pop(context, data).
  • For shared data across screens, use Provider (ChangeNotifier + Consumer pattern).
  • Deep linking lets users open a specific screen directly from a URL (App Links on Android, Universal Links on iOS).
  • The app has 4 lifecycle states: Resumed (visible, active), Inactive (brief transition), Paused (background), Detached (destroyed).
  • Use AppLifecycleListener to run code when lifecycle states change (onResume, onPause, onDetach).

Common mistakes to avoid

  • Forgetting context in Navigator.push() or Navigator.pop().
  • Not disposing resources (videos, streams, listeners) when the app goes to Paused or Detached.
  • Trying to update UI from a lifecycle callback without using setState() or Provider.
  • Confusing Inactive (brief transition) with Paused (background) — Inactive is temporary, Paused is sustained.
  • Assuming deep linking works automatically — you must configure it per platform (Android intent filters, iOS associated domains).
