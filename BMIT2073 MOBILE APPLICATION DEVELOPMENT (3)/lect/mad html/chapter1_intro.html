App Architecture

Types of mobile applications

When building a mobile app, you have three fundamental approaches. Each has trade-offs in cost, performance, and reach.

Native App

Built specifically for one platform using its native tools (Android Studio/Kotlin or XCode/Swift). Best performance, full device access, but separate codebases per platform = higher cost.

Hybrid / Cross-platform App

One codebase deployed to both platforms. Frameworks like Flutter and React Native compile to native code or render native components. Good balance of cost and performance.

Web App (PWA)

Runs in the mobile browser. No install required, but limited device access (no camera, GPS, etc. without browser APIs). Cheapest to build but least capable.

Comparison at a glance

Which one should you choose?

Need maximum performance and platform fidelity? Go native. Need to ship fast on a budget with good performance? Go cross-platform (Flutter). Need broad reach with minimal investment? A PWA might be enough.

Practice questions

Q1. What is the main disadvantage of native apps compared to cross-platform?
You need separate codebases for Android and iOS, increasing development time and cost.
Q2. What is the biggest limitation of a web app (PWA) compared to a native app?
Limited access to device hardware (camera, GPS, sensors, etc.) and lower performance.

Cross-platform frameworks

Flutter

Dart language, own rendering engine (Skia). Compiles to native ARM/x86 code. Best cross-platform UI consistency.

React Native

JavaScript/TypeScript, bridges to native components. Uses React paradigm. Good ecosystem but bridge overhead.

Xamarin

C#/.NET, compiles to native. Owned by Microsoft. Good for .NET ecosystem developers.

Kotlin Multiplatform

Share business logic across platforms via Kotlin, but keep native UI per platform.

Why Flutter stands out

Flutter does NOT use platform-native UI widgets (unlike React Native or Xamarin). It draws everything itself using Skia. This means your app looks the same on Android, iOS, Web, and Desktop — and you have full control over every pixel.

Practice question

Q1. What programming language does Flutter use?
Dart — an open-source, general-purpose, object-oriented, strongly typed language.
Flutter Architecture

Flutter's layered architecture

Flutter is organized into three layers. Understanding this helps you debug, optimize, and write better Flutter code.

Framework (Dart) Widgets, Rendering, Gestures, Animation, Material/Cupertino
Engine (C++) Skia graphics, Dart VM, text layout, platform channels
Embedder Android (Java/Kotlin), iOS (Obj-C/Swift), Web, Desktop

Layer breakdown

1
Embedder — the platform-specific entry point. Provides the host OS's event loop, renders onto a surface. Android has its own embedder in Java/Kotlin; iOS in Obj-C/Swift.
2
Engine — written in C++. Runs the Dart VM, compiles Dart to native code, handles graphics via Skia, manages text layout, and provides platform channels for native API calls.
3
Framework — the Dart layer you code against. Everything from MaterialApp and Scaffold to GestureDetector and AnimationController. Foundation → Rendering → Widgets.
Key insight — Flutter renders itself

Unlike React Native which bridges to native UI components, Flutter's engine paints every pixel via Skia. The platform embedder only provides a canvas (surface). This is why Flutter apps look identical across platforms.

Practice questions

Q1. What are the three layers of Flutter's architecture (top to bottom)?
Framework (Dart) → Engine (C++/Skia) → Embedder (Platform-specific).
Q2. What graphics library does Flutter's engine use for rendering?
Skia — a high-performance 2D graphics library.
Paradigm

Reactive UI — the Flutter way

Flutter uses a declarative, reactive UI paradigm. You describe what the UI should look like for a given state, and Flutter takes care of how to update it.

Declarative vs Imperative

Imperative (old way)Declarative (Flutter way)
How?You manually change the UI step by step: "find button, set text to 'hello', change color to blue"You describe what the UI should be: "if state is X, build this widget tree"
State changeYou mutate the UI directly (e.g., textView.setText(...))Framework rebuilds the affected part of the widget tree automatically
Bugs?Easy to miss a UI update — state and UI fall out of syncUI is always a function of state — they stay in sync by design

Flutter's data flow

1
Constraints go down — parent widgets tell their children the available space (max/min width and height).
2
Sizes go up — each child tells its parent how big it wants to be (within the constraints given).
3
Position is set — the parent positions the child based on layout rules (Row, Column, Stack, etc.).

State management landscape

Provider

Built on InheritedWidget. ChangeNotifier + Consumer. The recommended starter approach.

BLoC

Uses Streams/Sink pattern. Good for complex, testable state flows. More boilerplate.

Riverpod

Modern Provider successor. Compile-safe, no BuildContext needed, better testability.

App State vs Widget State

App State = shared data the whole app needs (auth token, user profile, cart).
Widget State = local, ephemeral data (text field input, animation progress, scroll position).
Use Provider (or Riverpod/BLoC) for App State; use StatefulWidget for Widget State.

Practice questions

Q1. What does "declarative UI" mean in Flutter?
You describe what the UI should look like for a given state, and the framework handles updating it. UI = f(state).
Q2. In Flutter's layout, what goes down and what goes up?
Constraints go down (parents limit children), sizes go up (children report their chosen size).
Q3. Name two approaches to manage App State in Flutter.
Provider, BLoC, or Riverpod (any two).

Exam revision — know these facts

  • Android + iOS control 99%+ of the smartphone market.
  • Three app types: Native (best performance, high cost), Cross-platform (good balance, one codebase), Web/PWA (cheapest, limited access).
  • For a highly interactive 3D game → choose Native (best GPU access, performance).
  • Flutter is cross-platform, uses Dart, and renders its own UI via Skia — NOT native components.
  • Flutter has 3 layers: Framework (Dart widgets) → Engine (C++/Skia) → Embedder (platform entry).
  • Declarative UI: you describe the desired state, Flutter rebuilds automatically.
  • Layout rule: constraints go down, sizes go up, position is set by parent.
  • Mobile constraints: limited battery, memory, unreliable network, small screens.

Common mistakes to avoid

  • Confusing declarative (what) with imperative (how) — in Flutter, describe the UI, don't mutate it.
  • Thinking Flutter uses native UI components — it does NOT; it paints everything via Skia.
  • Forgetting that mobile devices have real constraints — design for battery, memory, and network limits.
  • Assuming all cross-platform frameworks work the same — Flutter draws its own UI, React Native bridges to native components.
