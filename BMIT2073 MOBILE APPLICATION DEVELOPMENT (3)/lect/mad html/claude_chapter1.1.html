MODULE 1.1

Mobile OS, devices & problems

Lecture 1.1, slide 4–15

Before any app, you must know: what OS will run it, what device will run it, and what problems mobile devices have (compared to desktop computers).

Q1. What OS do most phones use today?

Answer

Two OS control almost all phones:

  • Android — made by Google, open-source, Linux kernel, uses Kotlin/Java
  • iOS — made by Apple, closed-source, only runs on iPhone, uses Swift/Obj-C

Remember for exam

Android + iOS = over 99% of all phones. Others (Harmony, KaiOS, Tizen, Fuchsia) are small / special-use only.

Q2. What are the mobile device tiers (classes)?

Answer

Devices are grouped by power level, from strongest to weakest:

Flagship

Newest CPU/GPU, lots of RAM, best screen. E.g. Galaxy S, iPhone Pro.

Mid-range

Balance of price vs speed. E.g. Galaxy A series, Redmi Note.

Entry

Basic speed, small storage. E.g. Nokia C series.

Basic

Feature phone, little or no apps. E.g. KaiOS feature phones.

Q3. What problems (challenges) do mobile devices have?

Answer

Mobile devices are smaller and weaker than PCs, so they have these limits:

  • Limited processing power — CPU is weaker (battery + heat limit)
  • Smaller memory (RAM) — apps must use memory carefully
  • Unreliable network — signal can drop, WiFi/data may be slow
  • Battery drain — heavy apps use battery fast
  • Small screen — less space to show content
Why this matters

Every design choice in Flutter (lazy lists, image caching, efficient rebuilds) exists because of these 5 mobile limits. Keep this in mind for Chapter 3 performance topics too.

App Architecture

Types of mobile apps EXAM: Q1a

Lecture 1.1, slide 17–19

There are 3 ways to build a mobile app. Each one trades cost vs speed vs reach.

Q1. What are the 3 types of mobile apps?

Answer

  • Native app — built only for one OS, using that OS's own tools
  • Hybrid / cross-platform app — one code, runs on both Android and iOS (e.g. Flutter)
  • Mobile web app (PWA) — runs inside the phone's browser, no install needed

Native App

Built only for one platform (Android Studio/Kotlin, or XCode/Swift). Best speed, full device access, but 2 separate codebases = higher cost.

Hybrid / Cross-platform App

1 codebase → both platforms. Flutter and React Native compile to native code. Good balance of cost and speed.

Mobile Web App (PWA)

Runs in browser. No install. But limited device access (camera, GPS need browser permission). Cheapest, but weakest.

Q2. Compare native, hybrid, and mobile web apps EXAM FORMAT

Exact exam question (Question 1a)

"Construct a table to briefly compare native, hybrid and mobile web apps based on FIVE criteria: Development cost, App performance, Distribution method, Access to device features, Code maintenance." (15 marks) — memorise this table exactly.

CriteriaNativeHybridMobile Web
Development costHigh — separate code for Android + iOSMedium — 1 codebase for bothLow — 1 codebase, no app store build
App performanceExcellent — direct access to hardwareVery good — near-native speedModerate — runs inside browser engine
Distribution methodApp Store / Play Store (must install)App Store / Play Store (must install)Just open a URL — no install, no store
Access to device featuresFull (camera, GPS, sensors, etc.)Full, via plugins/packagesLimited — only what browser APIs allow
Code maintenanceHard — must update 2 separate appsEasy — update 1 codebase for bothEasiest — update 1 web app, users get it instantly

Answer (Q1a-ii style)

Which app type is best for a highly interactive 3D mobile game? Why?
Native app. A 3D game needs the best possible performance and full, direct access to the GPU/hardware. Native apps give the fastest graphics rendering and lowest lag — hybrid and web apps add extra layers that slow this down.
Which one should you pick?

Need max performance/platform feel → go native. Need to ship fast on budget with good performance → go hybrid (Flutter). Need widest reach with least cost → a mobile web app may be enough.

More practice

Which app type needs an app store to be installed AND has the highest dev cost?
Native app — needs app store install, and needs 2 separate codebases (Android + iOS), so highest cost.
Which app type is easiest to maintain, and why?
Mobile web app — only 1 codebase, and updates apply instantly to all users (no store review needed).
Why does a hybrid app (like Flutter) have only "medium" development cost, not "low"?
It still needs to be built, tested, and submitted to both app stores (Android + iOS) — more work than a pure web app, even though it's 1 codebase.

Q2. What are the main cross-platform frameworks?

Flutter

Dart language, its own rendering engine (Skia). Compiles to native code. Best UI consistency across platforms.

React Native

JavaScript/TypeScript, connects (bridges) to real native UI parts. Big ecosystem, but bridge adds some overhead.

Xamarin

C#/.NET, compiles to native. Made by Microsoft. Good if you already know .NET.

Kotlin Multiplatform (KMM)

Share only the business logic across platforms, but each platform keeps its own native UI.

Why Flutter is different

Flutter does NOT use the phone's native UI parts (unlike React Native or Xamarin). It draws every pixel itself using Skia. This is why a Flutter app looks the same on Android, iOS, Web, and Desktop.

Flutter Architecture

Flutter's layered architecture

Lecture 1.1, slide 22–23

Flutter has 3 layers stacked on top of each other. Knowing this helps you understand how Flutter apps run.

Q1. What are the 3 layers of Flutter's architecture?

Answer

Framework (Dart) → Engine (C++) → Embedder (platform-specific).
Framework (Dart) Widgets, Rendering, Gestures, Animation, Material/Cupertino
Engine (C++) Skia graphics, Dart VM, text layout, platform channels
Embedder Android (Java/Kotlin), iOS (Obj-C/Swift), Web, Desktop

Q2. What does each layer actually do?

1
Embedder — the platform-specific starting point. Gives the OS's event loop, draws onto a surface. Android has its own embedder in Java/Kotlin; iOS in Obj-C/Swift.
2
Engine — written in C++. Runs the Dart VM, turns Dart into native code, draws graphics using Skia, handles text layout, and gives platform channels for calling native APIs.
3
Framework — the Dart code you write. Everything from MaterialApp and Scaffold to GestureDetector. Order: Foundation → Rendering → Widgets.
Key idea — Flutter paints itself

Unlike React Native (which bridges to real native UI parts), Flutter's engine paints every pixel using Skia. The platform embedder only gives a blank canvas (surface). That's why Flutter apps look the same on every platform.

The Engine layer — runs the Dart VM and uses Skia to draw graphics.

Paradigm

Reactive UI — the Flutter way

Lecture 1.1, slide 24

Flutter uses a declarative, reactive way to build UI. You describe what the UI should look like for a given state — Flutter decides how to update it.

Q1. What is the difference between declarative and imperative UI?

Answer

See table below.
Imperative (old way)Declarative (Flutter way)
How?You change the UI step by step: "find button, set text to 'hello', change colour to blue"You describe what the UI should be: "if state is X, build this widget tree"
State changeYou change the UI directly (e.g. textView.setText(...))Framework rebuilds the changed part of the widget tree by itself
Bugs?Easy to forget a UI update — state and UI go out of syncUI is always based on state — they stay matched by design

Q2. How does Flutter's layout data flow work?

1
Constraints go down — parent widgets tell their children the space they can use (max/min width and height).
2
Sizes go up — each child tells its parent how big it wants to be (inside the given constraints).
3
Position is set — the parent places the child based on layout rules (Row, Column, Stack, etc).

Q3. What state management options exist in Flutter?

Provider

Built on InheritedWidget. Uses ChangeNotifier + Consumer. Good starter approach.

BLoC

Uses Streams/Sink pattern. Good for complex, testable state flow. More code needed.

Riverpod

Newer Provider replacement. Compile-safe, no BuildContext needed, easier to test.

App State vs Widget State

App State = shared data the whole app needs (login token, user profile, cart).
Widget State = local, short-life data (text field input, animation progress, scroll position).
Use Provider/Riverpod/BLoC for App State; use StatefulWidget for Widget State.

Where to find it

Chapter_1_Merged.pdf — slide 24 (Reactive/Declarative UI, Data flow, State management).

More practice

What does "declarative UI" mean?
You describe what the UI should look like for a state, and the framework updates it. In short: UI = f(state).
In Flutter's layout, what goes down and what goes up?
Constraints go down (parent limits child), sizes go up (child reports its size back).
Name two ways to manage App State in Flutter.
Any two of: Provider, BLoC, Riverpod.

One-paragraph recap

  • Mobile OS: Android and iOS = over 99% of the market.
  • Devices come in 4 tiers: Flagship, Mid-range, Entry, Basic.
  • Mobile devices have 5 key limits: weak CPU, small RAM, unstable network, battery drain, small screen.
  • 3 app types: native (best speed, 2 codebases), hybrid (Flutter/React Native, 1 codebase), mobile web (cheap, limited device access).
  • Exam table: compare native/hybrid/web on Dev cost, Performance, Distribution, Device access, Maintenance.
  • Flutter: 3-layer build — Framework (Dart widgets) → Engine (C++/Skia rendering) → Embedder (platform entry point).
  • Declarative UI: describe what the UI should look like for the current state; Flutter updates it automatically.
  • Layout rule: constraints go down, sizes go up, position is set last.
  • State management: Provider, BLoC, Riverpod — pick based on app complexity.

Common mistakes to avoid

  • Mixing up the 5 comparison criteria — must be exactly: Dev cost, Performance, Distribution, Device access, Maintenance.
  • Thinking Flutter uses native UI parts — it does NOT; it paints everything itself with Skia.
  • Forgetting mobile devices have real limits — battery, memory, network, screen size.
  • Confusing declarative (describe what) with imperative (do how) — Flutter is declarative.
  • Thinking all cross-platform tools work the same — Flutter draws its own UI; React Native bridges to real native parts.
