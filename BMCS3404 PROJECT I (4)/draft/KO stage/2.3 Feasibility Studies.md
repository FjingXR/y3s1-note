# **2.3 Feasibility Studies**

**2.3.1 Technical Feasibility**

**Stack assessment.** Laravel 13 (PHP 8.5+) provides built-in Eloquent version columns for OCC, database queue for email dispatch, and Fortify for RBAC — covering all five objectives within a single framework. PostgreSQL 16 supports SERIALIZABLE isolation (SSI) required for OCC, `SKIP LOCKED` for FCFS queue polling, and JSONB for flexible slot metadata. Blade + TailwindCSS + Alpine.js avoids SPA overhead while meeting all UI requirements. Scale: 14 lecturers, 14 cohorts, 23 rooms, ~185 users — no performance bottleneck expected on localhost.

**Framework selection.** JetBrains Developer Ecosystem Survey (2024, 2025) reports Laravel at 61–64% PHP framework adoption. Castillo & Castellanos (2026) evaluated 7 MVC frameworks and ranked Laravel highest in learning curve and documentation quality — directly relevant for a single-developer FYP. Szewczyk & Skublewska-Paszkowska (2025) confirmed Laravel code compactness, with performance diverging only under data volumes far exceeding this project's <1,000 weekly slot intersections. Zajączkowski (2024) found Spring Boot 12× faster in CRUD benchmarks, but the system's true bottleneck is manual PDF scanning (minutes per search), not query latency (milliseconds).

**Database selection.** Ports & Grittner (2012) introduced Serializable Snapshot Isolation (SSI) in PostgreSQL — the first production RDBMS implementation, providing true serializability with <7% overhead over snapshot isolation. This directly enables the OCC strategy without pessimistic locks. A benchmark (Future Internet, 2024) found PostgreSQL 16 superior to MySQL 8.0 in complex transactional workloads (+14%) and analytical queries (3× faster), while MySQL's REPEATABLE READ permits phantom reads under write-skew (Berenson et al., 1995) — a risk for slot booking.

**Verdict:** Laravel's developer experience advantage at this scale, combined with PostgreSQL's SSI for OCC, makes the stack optimal for a single-developer FYP.

---

**2.3.2 Economic / Cost Feasibility**

All core technologies are open-source: Laravel (MIT), PostgreSQL (PostgreSQL license), TailwindCSS (MIT), and Alpine.js (MIT). Development runs on localhost (CachyOS) — no hosting, domain, or server costs. Mailtrap's free tier handles email testing; no paid APIs are required. Existing personal hardware meets all requirements, resulting in zero capital expenditure. Wheeler (2015) estimated that open-source software reduces total cost of ownership by 20–30% compared to proprietary alternatives, further supporting the financial viability of this approach.

---

**2.3.3 Operational Feasibility**

Target users are familiar with browser-based interfaces through TARUMT's Student Intranet and Staff Intranet portals. The three-tier RBAC (Student → Lecturer → PL) mirrors the existing organisational hierarchy — users learn no new permission model. The FCFS queue follows the current email-based workflow pattern (propose → await → approve/reject), requiring minimal process adaptation. The matrix intersection engine directly replaces manual PDF scanning (the most time-consuming step in §2.1.2), creating strong adoption incentive. Perceived usefulness — the strongest predictor of technology acceptance (Davis, 1989) — is maximised by targeting this clear pain point.

**Risk:** Moderate. Lecturers must transition from PDF + Google Sheets muscle memory to a new dashboard. Mitigated by: RBAC matching existing roles (no new permissions), FCFS flow matching current patterns, and a 2-click proposal → 1-click approval interface.

---

**2.3.4 Schedule Feasibility**

FYP1 (14 weeks): Proposal (2 wks) + Lit review & SRS (5 wks) + Design (3 wks) + Prototype (3 wks) = 13 wks (1 wk buffer). FYP2 (7 weeks): Implementation sprint (2 wks) + Integration (2 wks) + Testing (2 wks) + Report/Viva (1 wk). Five discrete modules (Matrix Engine, OCC, FCFS Queue, RBAC, Email) enable incremental delivery via time-boxed sprints. The most technically challenging features (Matrix Engine, OCC) are scheduled first, providing maximum testing time — consistent with Agile's risk-prioritisation principle (Sutherland & Schwaber, 2020). Total 21 weeks for 5 well-defined modules is realistic.

---

**2.3.5 Legal & Ethical Feasibility**

The system processes only timetable schedules, staff names, and cohort codes — none of which fall under Malaysia's Personal Data Protection Act 2010 (Act 709), which governs commercial transactions. TARUMT's existing data classification permits timetable visibility to staff and students. All development is localhost-based; no data crosses institutional boundaries.
