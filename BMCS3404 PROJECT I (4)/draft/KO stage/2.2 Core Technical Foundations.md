# **2.2 Core Technical Foundations**

**2.2.1 Optimistic Concurrency Control (OCC)**

- Originates from Kung & Robinson (1981) *"On Optimistic Methods for Concurrency Control"* — ACM TODS 

**Three-phase protocol:**

- Read Phase — transaction reads data, works on local copy  
- Validation Phase — before commit, system checks if data version has changed since read  
- Write Phase — if validation passes, changes committed; if fails, transaction is aborted and retried 

**Why OCC for this system:**

- Slot replacement is **low-contention** — most of the time, no two Lecturers are booking the same slot simultaneously → conflicts are rare → OCC performs better than pessimistic locks  
- **No deadlocks** — pessimistic row locks risk deadlock when two Lecturers edit overlapping slots; OCC avoids this entirely  
- **Millisecond precision** — integer version column check is atomic, sub-millisecond

**Version column pattern:**

- `time_slots` table has integer `version` column, default `1`  
- UPDATE query pattern:

| UPDATE time\_slots  SET status \= 'occupied', version \= version \+ 1  WHERE id \= :slot\_id AND version \= :old\_version |
| :---- |

- If `affected_rows === 0` → another transaction committed first → conflict detected → client retries  
- Laravel Eloquent supports this natively via `Model::optimisticLock()` pattern

**PostgreSQL serializable isolation as safety net:**

- Even if application-level OCC misses a conflict, PostgreSQL's `SERIALIZABLE` isolation detects phantom reads and aborts conflicting transactions automatically  
- Two-layer defense: app-level OCC (version column) \+ DB-level (serializable isolation) 

**Contrast with Google Sheets (current workflow):**

- Google Sheets has **zero concurrency control** — two Lecturers editing the same row causes silent overwrite  
- OCC guarantees that if a slot was booked between read and write, the second writer is notified and must retry

**2.2.2 Matrix Intersection Algorithm**

- Computes the **intersection** of four availability sets in real-time: **Lecturer Availability ∩ Cohort A Timetable ∩ Cohort B Timetable ∩ Room Vacancy**  
- Each set is a collection of (day, time\_slot, week) tuples 

**Algorithm steps:**

1. Fetch lecturer's available slots (via `lecturers.availability` or unallocated time in timetable)  
2. Fetch Cohort A's free slots (timetable gaps where no class is scheduled)  
3. Fetch Cohort B's free slots (affected cohort — replacement class must not clash with their existing classes)  
4. Fetch room vacancy (room not in use at the proposed time)  
5. **Intersect all four** — only slots present in all sets are valid 

**Why this differs from traditional timetabling:**

- Full timetabling (aSc, FET, Unitime) solves **NP-hard constraint satisfaction** — placing all classes across a semester  
- Matrix intersection solves **real-time slot search** — given existing fixed schedules, find gaps common to all parties  
- Babaei, Karimpour & Hadidi (2015) classify timetabling approaches; this system fits under *"interactive/ad-hoc rescheduling"* not *"batch generation"*  
- Al-Hawari, Alouneh & Barham (2020) systematic review confirms that **post-hoc replacement** is understudied compared to initial timetable generation

**Computational complexity:**

- Each set is typically small (≤ 50 slots per entity per week) → intersection runs in O(n × m) or less  
- For 14 cohorts \+ 14 lecturers \+ 23 rooms, worst-case intersection size \<\< 1,000 slots → no performance concern on localhost  
- Implemented via Laravel Collections (`->intersect()`) or PostgreSQL `ARRAY_AGG` \+ `&&` array overlap operators 

**Contrast with current PDF scanning (step 2 in §2.1.2):**

- Currently: lecturer manually scans PDFs → mental intersection → error-prone  
- Proposed: automated set intersection → instant valid slot list → no human error

**2.2.3 Slot State Machine (Available → Pending → Occupied)**

- Each replacement slot follows a strict state lifecycle:

| Available     │     ▼ (Lecturer proposes slot)  Pending     │     ├──► (PL approves) → Occupied     │     └──► (PL rejects)  → Available (slot freed) |
| :---- |

- **3 actual states in the database:** 

| State | What It Means |
| :---- | :---- |
| Available | Slot is free, any Lecturer can propose |
| Pending | Lecturer submitted request; waiting for PL approval; slot locked from other proposals |
| Occupied | PL approved \+ original class conducted; terminal/archival state |

- **Display mapping (what each role sees in the UI):** 

| Actual DB State | Proposing Lecturer Sees | Other Lecturers See | PL Sees |
| :---- | :---- | :---- | :---- |
| Available | Available | Available | Available |
| Pending | Pending | Reserved (taken by another) | Pending (in FCFS queue) |
| Occupied | Occupied | Occupied | Occupied |

- "Reserved" is a **display label only** — communicates to other Lecturers: "someone already claimed this slot, don't propose it"  
- The DB has 3 states; the UI shows 4 statuses depending on who's viewing 

**Why a state machine:**

- **Prevents race conditions** — a slot cannot be double-proposed (Pending locks the slot until PL decides)  
- **Maps directly to real-world workflow** — mirrors the Lecturer→Propose→PL→Approve lifecycle from §2.1.2  
- **Audit trail** — each state transition records timestamp \+ actor → full accountability  
- **RBAC integration** — each state maps to visibility rules:  
  - Available → visible to all Lecturers  
  - Pending → visible to proposing Lecturer , (other Lecturers see "Reserved")  
  - Occupied → visible to all (historical record) 

**Combined with OCC (double safety):**

- State machine prevents **logical** conflicts (slot in wrong state)  
- OCC prevents **concurrent** conflicts (two transactions modifying same slot simultaneously)  
- A valid transition requires: correct current state **AND** unmodified version column
