# 2.4 Feasibility Studies

This section evaluates the proposed system across five dimensions — technical, economic, operational, schedule, and legal — to determine whether the project is viable within the constraints of a Final Year Project at TARUMT Sabah.

## 2.4.1 Technical Feasibility

The proposed technology stack consists of Laravel 13 (PHP 8.5+), PostgreSQL 16, TailwindCSS, Alpine.js, and Blade — all of which are open-source and well-established within the web development ecosystem. Laravel provides built-in support for Eloquent version columns (enabling Optimistic Concurrency Control without external packages), a database-backed queue driver for asynchronous email dispatch, and Laravel Fortify for session-based RBAC — collectively covering all five project objectives within a single framework. JetBrains (2024; 2025) reports Laravel at 61–64% adoption among PHP developers, confirming its position as the dominant PHP framework globally. Castillo and Castellanos (2026) empirically evaluated seven MVC frameworks using a multi-criteria decision model and ranked Laravel highest in learning curve and documentation quality — characteristics directly relevant to a single-developer academic project where rapid onboarding and community support are critical. Szewczyk and Skublewska-Paszkowska (2025) confirmed Laravel's code compactness at this project's data volume, while Zajączkowski (2024) found Laravel's CRUD performance adequate — the true bottleneck is human PDF scanning, not framework throughput.

PostgreSQL 16 was selected over MySQL due to its unique concurrency control capabilities. Ports and Grittner (2012) introduced Serializable Snapshot Isolation (SSI) in PostgreSQL as the first production RDBMS implementation of this technique, providing true serializability with less than 7% performance overhead compared to snapshot isolation — directly enabling the OCC-based slot validation strategy. A comparative benchmark (Future Internet, 2024) found PostgreSQL 16 superior to MySQL 8.0 in complex transactional workloads (+14% throughput) and analytical queries (3× faster), while MySQL's REPEATABLE READ isolation level permits phantom reads under write-skew conditions (Berenson et al., 1995) — a risk that cannot be tolerated for millisecond-precision slot booking. PostgreSQL's SSI directly prevents the double-booking problem identified in §2.1.2, where two Lecturers editing the same Google Sheet row caused silent overwrites that went undetected until downstream conflicts emerged. The PostgreSQL Documentation (2026) formally defines the SERIALIZABLE isolation level and its implementation via Serializable Snapshot Isolation, confirming its suitability for transaction-safe slot booking. OCC version columns maintain data integrity without locking, satisfying academic record-keeping requirements.

The Laravel Documentation (2026) provides canonical references for the built-in features used — Eloquent ORM for version column OCC, the database queue driver for email dispatch, and Blade templating for the dashboard UI — confirming that no external packages or custom infrastructure are needed. The full stack is well-documented within the PHP ecosystem, reducing implementation risk.

Scale is modest: 14 lecturers, 14 cohorts, 23 rooms, and approximately 185 users. At this level, framework-level performance differences are negligible — the bottleneck in the current workflow is human PDF scanning (minutes per search), not database query latency (milliseconds). Laravel's built-in scaffolding tools (Artisan, migrations, Eloquent) further reduce boilerplate development time. The proposed stack is technically capable of delivering all required functionality within the project's scope and constraints.

## 2.4.2 Economic Feasibility

All core technologies are open-source and carry no licensing cost: Laravel (MIT), PostgreSQL (PostgreSQL license), TailwindCSS (MIT), and Alpine.js (MIT). Development is conducted entirely on localhost (CachyOS), eliminating hosting, domain, and server expenditure. Mailtrap's free tier is sufficient for email testing during development. No paid application programming interfaces or third-party services are required, and existing personal hardware meets all system requirements. Wheeler (2015) estimated that open-source software reduces total cost of ownership by 20–30% compared to proprietary alternatives, further supporting this conclusion. The project therefore carries zero direct financial cost.

## 2.4.3 Operational Feasibility

Target users at TARUMT Sabah are already familiar with browser-based interfaces through the Student Intranet and Staff Intranet portals, reducing the adoption barrier for a new web-based system. The three-tier RBAC (Student, Lecturer, Programme Leader) mirrors the existing organisational hierarchy — users are not required to learn an unfamiliar permissions model. The First-Come-First-Served (FCFS) approval queue follows the same workflow pattern as the current email-based process (propose, await validation, receive outcome), minimising process adaptation. More importantly, the matrix intersection engine directly replaces the most time-consuming step identified in §2.1.2 — manually scanning PDF files to find available slots — replacing it with automated, real-time intersection. Perceived usefulness is the strongest predictor of technology acceptance (Davis, 1989), and this feature directly targets a clearly felt pain point in the current workflow. The FCFS queue also provides the audit trail and state tracking that are entirely absent from the current Google Sheets approach.

Adoption risk is moderate, as Lecturers must transition from PDF and Google Sheets to a new interface. This is mitigated by the interface mirroring existing role structures and by keeping the interaction model simple: two clicks to propose a slot, one click to approve or reject.

The project is planned across two semesters. Five discrete modules (Matrix Engine, OCC, FCFS Queue, RBAC, Email) enable incremental delivery within time-boxed sprints.

## 2.4.5 Legal and Ethical Feasibility

The system processes only timetable schedules, staff names, and cohort codes — data that does not fall under Malaysia's Personal Data Protection Act 2010 (Act 709). TARUMT's existing data classification permits timetable visibility to staff and students. All development is performed on localhost, ensuring no data crosses institutional boundaries. No legal or ethical barriers to implementation have been identified.
